## 猎鹰 SDK 评估（用户问"能否加快/精准定位"）

- **猎鹰 = 高德「轨迹服务」AMapTrack，不是定位增强服务**。核心能力：轨迹上传/云存1年/查询、
  **轨迹纠偏·绑路·补路**（把漂移点吸附到正确道路、轨迹平滑）、里程计算、驾驶行为分析、轨迹围栏。
- **澄清用户直觉**：
  - "加快定位" —— **不对**。猎鹰不产位置，定位速度/精度由定位 SDK + 硬件（GPS/北斗 + AGPS 辅助）决定，
    与猎鹰无关。要加快首定位得在定位 SDK 配置（混合定位/AGPS）上做。
  - "把定位搞更精准" —— **对一半**：猎鹰纠偏让**记录的轨迹线**更贴路平滑，是事后/云端处理，
    不是把"实时坐标"变准。
- **对项目价值**：唯一契合点是让"轨迹回放/分享"那张图更贴路平滑；但代价偏高 —— 又一套 so（需重验
  16KB 内存页 `p_align`）、纠偏要**上传高德云端**（车机离线导航时失效）、用户轨迹出本地到第三方。
  结论：**不建议为猎鹰堆 so**。需要轨迹更平滑时，用已有的 `SpatialRelationUtil` 路网吸附做**本地轻量
  纠偏**即可，符合项目"SDK 有能力但故意不换/不堆"的克制原则。
- 其余免费服务：地图/定位/导航 SDK **已在用**；室内地图/室内定位是商场楼宇场景，车机户外导航用不上。
- **结论**：用户采纳"本地轻量轨迹纠偏"方案（不用猎鹰）。

## 重大修正：本项目根本没集成"导航 SDK（AMapNavi）"

- **事实**：全代码库 `import com.amap.api.navi` 一条都没有；实际只用**地图 SDK + 定位 SDK + 搜索 SDK**。
  所谓"导航"是 `RouteNaviEngine` 自研引擎（路线规划借搜索 SDK 的 `RouteSearch`、定位借定位 SDK、
  吸附借地图 SDK 的 `SpatialRelationUtil`）。工作记忆里写满的 `AMapNavi` 是**错误记忆**。
- 因此上文"导航 SDK 电子眼/限速 updateCameraInfo"那段**作废**：我们压根没接 AMapNavi，谈不上"没接回调"。
- **电子眼/限速结论**：只存在于高德**导航 SDK**，搜索 SDK 的 `DrivePath/DriveStep` 里没有（只有 TMC 路况、
  红绿灯、收费、限行）。要电子眼/限速**必须接入 AMapNavi**——是大任务（新初始化/隐私/路线数据源全换），
  不塞进本次发版。
